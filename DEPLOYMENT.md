# InternLink: hosting the feature branch

This repository is a monorepo with `client/` (Next.js) and `server/` (Express). The current deployment candidate is **`feature/internlink-proposal-completion`**. Do not merge or deploy `main` accidentally.

## 1. Deploy Express on Render

Sign in at https://dashboard.render.com and connect GitHub. Two supported methods:

### Manual web service (simplest)
- New > **Web Service** > repository `hansajadamneth-lgtm/TeamVertex_Intern-Link`
- **Branch**: `feature/internlink-proposal-completion`
- **Language**: Node
- **Root Directory**: leave blank (the root contains the npm workspaces)
- **Build Command**: `npm install` (the branch currently has no root `package-lock.json`; use `npm ci` only after committing a root lockfile)
- **Start Command**: `npm run start --workspace=server`
- **Health Check Path**: `/api/health`
- Choose a suitable region/plan (the free plan may sleep when inactive)

### Blueprint method
The repository includes `render.yaml` for the same Node web service. Select this feature branch when creating a Render Blueprint. Fill in any prompted environment variables; do not add secrets to Git.

Add environment variables in Render:

| Name | Value |
|---|---|
| `NODE_ENV` | `production` |
| `MONGO_URI` | Atlas MongoDB URI (**secret**) |
| `JWT_SECRET` | Long, random secret (**secret**; generated by the Blueprint if used) |
| `CLIENT_URL` | Final HTTPS Vercel production URL, without trailing slash |

Render supplies `PORT`; do not force a local port. For the first backend deploy, `CLIENT_URL` can be temporarily set to a known planned origin and then updated after Vercel assigns the real domain. After deployment, verify:

`https://YOUR-SERVICE.onrender.com/api/health`

A 200 response only establishes that Express is responding; confirm database connectivity in Render logs and test authenticated routes afterward.

**Atlas IP allowlist:** The Render service must be allowed to connect to Atlas. Use controlled outbound IP addresses where available, or an explicitly accepted broad network rule for limited testing. If you temporarily allow `0.0.0.0/0`, understand it permits connections from any IP; retain strong database credentials and tighten access as soon as possible.

## 2. Deploy Next.js on Vercel

At https://vercel.com/new import the **same GitHub repository**.

- **Project Name**: e.g. `internlink-web`
- **Framework Preset**: Next.js
- **Root Directory**: `client`
- **Build Command**: default `next build` (or `npm run build`)
- **Production Branch**: `feature/internlink-proposal-completion`, **not** `main`. Configure in **Project Settings > Environments > Production > Branch Tracking**, then deploy the feature branch.

Set these variables for the **Production** environment:

| Name | Value |
|---|---|
| `BACKEND_URL` | `https://YOUR-SERVICE.onrender.com` |
| `NEXT_PUBLIC_APP_URL` | `https://YOUR-PROJECT.vercel.app` |

**Important:** `BACKEND_URL` is a server-side value. Browser requests go through Next.js `/api/*` routes so login cookies remain associated with the frontend origin. Do not set it to `localhost` or prefix it with `NEXT_PUBLIC_`. Changes to environment variables require a redeploy.

## 3. Connect both and verify

After Vercel deployment, set Render `CLIENT_URL` to the exact assigned Vercel URL (or custom domain), including `https://`, and save/redeploy if needed. If using several known frontend domains, Render supports comma-separated `CLIENT_URL` origins.

Visit:
- `https://YOUR-PROJECT.vercel.app/api/health`: should proxy the Render health response
- `https://YOUR-PROJECT.vercel.app/home`: should display the frontend
- `/register` and `/login`: verify real registration/login
- `/api/auth/me`: should report current user after sign-in
- CV Builder and Applications: verify authenticated API requests and persistence
- Sign out: verify authenticated API requests return 401 afterward

For a deployment test, use a fresh test account and avoid sharing credentials in chat. The mock resume upload, placeholder notification data, and some admin/demo screens are not necessarily connected to persisted production data. Audit features and permissions before promoting this university prototype to real users.

## 4. Troubleshooting

- Vercel 503 for API: inspect Render service logs, then check Vercel `BACKEND_URL`.
- Render cannot connect to MongoDB: check `MONGO_URI`, Atlas network access, database user permissions.
- Register/login works but CV routes say 401: check browser cookies for the frontend domain. Backend auth cookies use `path: '/'` so all proxied API routes can access them; ensure the feature branch includes this fix.
- CORS error: Render `CLIENT_URL` must match the exact HTTPS frontend origin.
- Render free service sleeping: first request can be slow. Check plan limitations.

Never commit `.env` files or live credentials. Deploy the feature branch only, keeping `main` unchanged.

## Triggering Vercel after changing Production Branch

Vercel automatically creates a production deployment on new commits pushed to the tracked production branch. If the initial import was cancelled while it targeted `main`, configure Project Settings > Environments > Production > Branch Tracking to `feature/internlink-proposal-completion`, save it, and push a new commit to that feature branch. Check the Vercel Deployments tab to confirm the deployed branch and commit SHA. This step never requires editing or merging `main`.
